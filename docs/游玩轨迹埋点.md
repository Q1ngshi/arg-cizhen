# 游玩轨迹埋点系统设计文档

> 2026-08-12 定稿。目标：朋友/玩家游玩后，总经理拿到一份"走到哪、卡在哪"的操作轨迹。

---

## 一、设计目标

1. **采集**：玩家每一步关键操作自动记录（localStorage，跨官网/桌面共享）
2. **回收**：零后端——轨迹随「交接班」记录一并复制，玩家微信发给总经理
3. **分析**：轨迹 → 对照漏斗 → 定位"最后止步于哪一步、每步耗时多少"

## 二、核心机制

```
埋点 logStage(k, extra)  →  cz_stage_log = [{k:'gate_ok', e:'linyuan', t:时间戳}, ...]
        （官网/桌面同源，localStorage 共享）
                ↓
交接班生成 → 尾部追加【系统操作日志】节（序号 · 节点 · 相对时间）
                ↓
玩家点「复制记录」→ 微信发总经理 → 总经理对照漏斗分析
```

- 时间戳用 `Date.now()`（meta 层真实时间，不进叙事），日志显示为**相对第一步的分钟数**
- 时间戳去重：同一 key 只记第一次（玩家反复试密码只记首次）
- 上限 60 条（防溢出）

## 四、报告格式（交接班附注）

```
—— 附：系统操作日志（本班）——
01 官网 打开 · 0:00
02 检索 关键词:林远 · 0:02
03 密码门 打开 · 0:05
04 密码门 尝试失败 · 0:07
05 卷宗解锁 linyuan · 0:09
...
```

- 系统口吻（"检索 关键词"），不破坏伪装
- 相对时间 = 距第一步的分钟（0:00 / 0:05 / 1:12）

## 五、基调三问

1. **削弱伪装？** 否。值班记录附操作日志 = 档案系统监视感的强化，不是游戏 UI
2. **直白说破？** 否。日志只有操作名和时间，不含"你卡住了"评价
3. **破坏打工循环？** 否。日志本身就是打工痕迹（整理档案 = 被记录）

## 六、分析流程（总经理拿到日志后）

1. 日志文本 → Claude → 对照漏斗表逐条编号
2. 输出：**最后止步节点 + 每层耗时 + 卡点判断**（未触发的下一层 = 卡点）
3. 汇总多人轨迹 → 漏斗流失最重的层级 = 引导薄弱处 → 修

## 七、实现要点（防回归）

- `logStage` 双端各一份（官网 index.html / 桌面 desktop.html），key 命名空间一致
- localStorage 键 `cz_stage_log`，JSON 数组，同源共享（localhost 与线上域名各自独立，互不污染）
- 交接班日志节：只读不删（多次生成交接班重复输出日志节，玩家任取一次）
- 日志上限 60 条，超过丢最旧
- 去重：同 key 同 extra 只记首次（存于日志数组自身，无额外状态；刷新后仍不重记 = "一次操作一条"，避免反复试密码刷屏）
